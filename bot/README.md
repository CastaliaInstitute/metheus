# Metheus Matrix AI bot

This is the server-side companion for the static client in [`/chat/`](../docs/matrix-chat-pwa.md). It joins only explicitly allowlisted rooms, requires Matrix end-to-end encryption, and processes only explicit AI commands such as `!metheus ask …` or `!metheus ask-chart …` after the room-wide consent gate passes.

## Shared-room consent gate

Before any AI request, every currently joined person other than the bot must:

1. Send `!metheus ai-info` and receive the disclosure in the room.
2. Send `!metheus ai-opt-in`.
3. Use `!metheus ai-status` to see aggregate informed/opt-in counts and whether explicit AI questions are active; individual choices are not listed.

Ordinary room messages are never forwarded. The bot keeps a short conversation context in memory only. It clears that context when any room member joins or leaves, when any participant opts out, and after a process restart. If membership, consent, or a chart setting changes while a model request is running, the bot discards both the model reply and any failure notice. Any request already sent to the provider cannot be recalled. Membership changes are detected against the current room state before commands and after each model call; a consent revision also invalidates the in-flight response even if the room later returns to unanimous opt-in.

`!metheus ai-opt-out` pauses the room immediately and clears in-memory context. The room must complete the disclosure/opt-in flow again to resume. The bot host stores per-room informed/opted-in Matrix user IDs and a membership signature in `room-consent.json`; this file contains no messages. Matrix sync state and encryption keys are stored separately in the configured data directory. Restrict the host, volume, backups, and operator access accordingly.

The model request uses the OpenAI Responses API with `store: false`, no `previous_response_id`, and a bounded in-memory exchange. This disables Responses API application-state storage but does not guarantee zero retention: provider abuse-monitoring controls and retention vary by account and may retain content. The room disclosure directs members to review the provider's current terms before sharing sensitive, health, child, reproductive, or intimate information. The bot does not claim that Matrix encryption hides content from the bot or the configured AI provider.

Each question sent to the model is prefixed with a room-local ordinal label (for example, “Room participant 2”), based on the current member ordering. This helps distinguish speakers in a shared exchange without sending Matrix user IDs. The label is temporary context, not an identity claim or a durable profile; membership changes clear the conversation context.

For an explicit AI question that mentions a gate number, including a chart-aware turn, the bot may add matching entries from `catalog/gate-endocrine-correspondences.json`; the room disclosure tells participants this may happen. These entries preserve source lineage and limitations so the model can describe a teaching as source-attributed; they are not passed as biological facts or used to infer a room member's physiology. If the catalog is missing, the bot continues without correspondence context and is instructed not to invent gate/hormone links. Set `METHEUS_CORRESPONDENCE_CATALOG` if the deployment keeps this catalog outside the repository's default relative path.

The one-turn command `!metheus ask-chart my-gates: 11, 56 | <question>` requires the sender's `my-gates:` self-attestation. The bot cannot authenticate chart ownership. This is a user-supplied, non-time-bound personal gate list; the current path does not calculate transits or describe live gate activations. The `!metheus chart-set my-gates: 11, 56` alternative applies to that sender's own future explicit `!metheus ask` turns until `!metheus chart-clear`, any room opt-out, a membership change, or process restart. `!metheus chart-status` lets a sender check only their own setting; room-level `ai-status` never lists individual settings. All current room members must also have opted into AI processing. On each chart-aware turn, the bot derives complete channels, centers, and a complete, unranked candidate pool of complementary activities from the version-matched topology and AI-affordance catalogs, then sends that context with the sender's current question only. Chart-aware turns neither receive prior shared-room AI conversation nor add their question or answer to that memory, so one participant's gate context cannot shape another participant's prompt through bot-side history. Replies and commands remain visible in Matrix room history. Each gate activity includes controlled interaction-mode labels such as `compare`, `reflect`, or `coordinate`; these tell the model what kind of help the catalog activity offers and are not user traits. The model should adapt the response to the sender's stated goal and may offer at most one activity from the complementary candidate pool when it clearly helps; candidates are not ranked by chart alone. Gate lists are not independently calculated or verified. The bot keeps the optional `chart-set` gate list in process memory only and never writes it to its data directory. Catalog references are optional design prompts, not evidence of need, deficit, ability, biological effects, or literal gate activation. If either catalog is missing or version-mismatched, chart-aware requests are disabled. Set `METHEUS_TOPOLOGY_CATALOG` and `METHEUS_GATE_AI_AFFORDANCE_CATALOG` if deployment paths differ from the repository defaults.

For questions involving babies or children, the bot is instructed to address the caregiver, respect a child's voice and assent as appropriate, rely on concrete observations and context, and avoid developmental scoring or chart-derived expectations. It is not a caregiver, attachment figure, screener, or source of feeding, sleep, or learning regimens. Personal child concerns should go to an appropriate pediatric or developmental professional. This conversational instruction is not a substitute for the privacy, stewardship, and consent controls required before collecting or processing child data; the prototype should not be used for children's personal data.

The current Matrix Bot SDK dependency tree includes legacy `request`-family packages with unresolved moderate advisories. A compatible maintained request implementation is pinned by npm override to remove the critical/high advisories in the older package, but that does not substitute for dependency review or a security audit. This service is an integration prototype; do not deploy it with sensitive user data until those upstream dependencies and the full deployment have been reviewed.

## Configuration and run

The repository includes a Docker deployment for a persistent bot process. It keeps the bot's Matrix crypto state in a private named volume, runs as the unprivileged Node user, exposes no network port, and reads credentials from the ignored `bot/.env` file. The image contains the bot code and the versioned catalogs it requires.

1. Create a dedicated Matrix bot account. Create a private, encrypted test room and note its exact room ID. Keep the bot account restricted to rooms that you explicitly operate.
2. Copy `bot/.env.example` to `bot/.env`, set its Matrix homeserver, bot access token, exact allowlisted room ID, model API key, and enabled model. Keep this file private; `.gitignore` excludes it. Do not put a bot token or model key in the PWA, a room message, or source control.
3. Invite the bot account to the encrypted test room. Start the service from the repository root:

```sh
docker compose up --build -d metheus-bot
docker compose logs -f metheus-bot
```

4. In the room, send `!metheus ai-info`, read the disclosure, then send `!metheus ai-opt-in`. Each other room member must do the same. Check `!metheus ai-status`; only after every current member has opted in will explicit AI questions be processed.
5. In the PWA, sign in with your own Matrix account, enter the same room ID, and check that the room is encrypted. Try a regular `!metheus ask` or a one-turn chart request. Chart-aware prompts must contain only your own self-attested gates.

Stop the local service with `docker compose down`. The named `metheus-bot-data` volume is retained so Matrix crypto state survives container restarts; back it up and restrict host access. Removing that volume resets device state and must be treated as a bot-device recovery operation.

For a direct local Node run instead, copy the same settings into the environment, install with `npm ci --prefix bot`, and run `node bot/src/index.mjs` from the repository root. The bot requires Node.js 22 or later.

Required settings are `MATRIX_HOMESERVER_URL`, `MATRIX_BOT_ACCESS_TOKEN`, `MATRIX_ALLOWED_ROOM_IDS`, `OPENAI_API_KEY`, and `OPENAI_MODEL`. `OPENAI_BASE_URL` is optional and selects an OpenAI-compatible Responses API endpoint. For a local Ollama instance, the OpenAI SDK still requires a placeholder key, which Ollama ignores: use `OPENAI_API_KEY=ollama`, `OPENAI_BASE_URL=http://host.docker.internal:11434/v1`, and a model already installed in Ollama, such as `qwen3:8b`. The Matrix bot container then sends model requests to the host's Ollama service; the local test does not require an OpenAI API key. Do not use this local endpoint configuration for a remotely hosted Ollama server without configuring transport security and access controls. The bot uses the Matrix Bot SDK's Rust-backed SQLite crypto store and requires a supported Node.js runtime and platform binary. The deployment operator must verify the bot device and confirm the actual homeserver, provider, account retention settings, and room history policy before inviting participants. A successful container start only proves that the process initialized; `!metheus ai-status` and a harmless test question in the encrypted, fully opted-in room verify end-to-end operation.

The PWA can add `metheus-gates: 17, 62 |` after the user gate list in a one-turn command, for example `!metheus ask-chart my-gates: 11 | metheus-gates: 17, 62 | <question>`. This separate set is a user-configured Metheus prompt profile, not an AI-owned chart or lived experience; it is delivered only for that command and is not stored by the bot. The model receives the user map and Metheus profile under separate labels and is instructed not to infer compatibility, traits, needs, or biology from their overlap.

## Current boundaries

The bot does not create rooms, manage human accounts, persist Metheus profiles or chart data, read ordinary room history, provide device-verification/recovery UX, store transcripts, export/delete Matrix room history, moderate a family, or provide therapy, clinical care, or emergency response. A sender may submit their own gate list for one request or explicitly enable a temporary in-memory room setting; neither path calculates or verifies a chart. Its Matrix crypto setup is an implementation component; this prototype has not received a security audit or operational deployment review. It must not be used for children's personal data or sensitive health/intimacy discussions until those reviews and the required product controls are complete.
