# Metheus Circle: Matrix chat PWA

**Status:** static client prototype. It connects individual Matrix accounts to an existing room. The PWA does not host rooms, collect profiles, or provide the Metheus AI service.

## What it does

The installable client at `/chat/` signs a person into the Castalia Matrix homeserver through Castalia.Institute single sign-on, joins or opens a room ID/alias, displays room text messages, and sends a new text message. The client uses Matrix's SSO redirect and one-time `m.login.token` exchange; it does not ask for or handle a Castalia password. A random state value binds the callback to the browser session, the callback strips the login token from the URL before loading the app module, and the exchanged session token stays in memory. The Matrix SDK and Rust-backed crypto runtime load only after sign-in; the production build keeps them out of the initial UI bundle. Shared-room messages are visible to the room's members. Matrix SDK encryption state uses browser IndexedDB. The service worker caches only the application shell and static assets; it does not cache Matrix API responses or room messages. The app does not retain transcripts in its own storage. The client queries the SDK for the room's encryption setting and disables sending if Matrix reports encryption is off; it does not independently verify users' devices or the bot's key handling.

The PWA is a presentation and transport client. An independently operated Metheus Matrix bot must join the room and respond to messages for users to chat with Metheus AI. A prototype bot is now included in [`bot/`](../bot/README.md), but it is not deployed or connected to the Pages client. It requires a separately operated Node service, an allowlisted Matrix bot account, persistent private crypto storage, and a server-side OpenAI API key. The PWA has no model/API key or direct model connection.

The BodyGraph panel includes a searchable catalog of 64 optional AI activity ideas, one per gate, each with a plain-language example prompt. “Use as a regular AI question” fills the composer with the example under `!metheus ask`; it does not send the message or append a gate list. If the sender has enabled `chart-set`, that setting still makes their own `ask` chart-aware. A participant can optionally mark gates they self-report as active for them. This is a user-supplied, non-time-bound personal gate list: the current bot does not verify a chart or calculate transits. “Ask once with my active gates” prepares a one-turn `!metheus ask-chart my-gates: … | …` draft. Before sending, the selection panel shows the activity ideas linked to selected gates, shows the two activities for any complete channels, and previews possible activities for partner gates, grouped by channel and explicitly unranked. The AI may combine the paired activities when useful to the stated question; the symbolic channel label is not a fixed trait or biological mechanism. This makes the chart-linked activities and optional complements visible for review. “Use my gates for future asks” prepares `!metheus chart-set my-gates: …`, which enables those self-attested gates for that sender's later explicit `!metheus ask` turns in the room; `!metheus chart-clear` removes the setting. The profile stays in bot memory only and clears on opt-out, room membership change, or bot restart. Chart-aware replies use that sender's current question and chart context alone, without any earlier chart-aware or shared conversation history. On each chart-aware turn, the bot receives the complete selected gate list, linked channel map, and linked activities, then assesses the activities against the stated question. It can shape its practical help around a relevant activity and offer at most one partner-gate activity when it adds a useful option. It answers the question first and may omit chart framing when no activity fits. These suggestions are optional and do not activate gates or establish missing abilities. Because earlier chart-aware replies are not included, the AI cannot reliably remember which activities it suggested before or what the person thought of them. PWA gate selection is temporary in the browser and is not chart verification. The catalog is a static copy of `catalog/gate-ai-affordances.json`; contract validation checks that the PWA copy stays synchronized and that the BodyGraph reference SVG carries the same topology catalog ID and version as the catalog source; the client compares the SVG gate centers and channel pairs with the activity catalog at load time.

Each gate card now has **Record trying this activity** for an activity the person has already tried. The local composer exports a JSON array containing a self-reported `environmental_affordance` use event and, if the person enters a category or note, a separate self-reported experience observation linked to that event. It requires a pseudonymous participant label and use date; the activity event is date-only, while an optional experience report is timestamped when entered. Records default to personal/private and subject-controlled. The person can state the intended function, and AI identity/privacy/role disclosures are marked `not_observed` rather than assumed. Gate and channel tags are omitted unless the person explicitly selects **Include the selected gate and its channel references**; this adds only the card's gate context, not their full chart. The file is generated in the current browser session and is not sent to Matrix, the AI provider, or local storage. It does not include chat text or an AI reply and does not establish gate activation, channel completion, benefit, harm, hormone change, or causation. The person controls whether to retain or share the download.

The **AI activity use and experience** local viewer can open the summary JSON produced by `tools/summarize_affordance_trial.py`, or show a bundled synthetic example. It renders lifecycle events, subjective reports, and recorded temporal comparisons as separate text lists and displays the summary's limitations. The viewer checks required fields and record references before display, but the summary file is not proof of identity, consent, authorization, or source-record correctness. The selected file stays in the current tab and is not sent to Matrix or an AI provider.

The BodyGraph panel also has optional local cycle-day and measurement viewers. “Preview synthetic example” demonstrates each layout without personal data. A person can open a JSON view generated by `describe_authorized_reported_cycle_day_view` after explicitly selecting and authorizing its marker and observation records; the client displays the reported calendar offsets, not a hormonal phase or cycle-health assessment. A person can also open a JSON result from `summarize_numeric_measurements`, showing the named signal/analyte, units, method and source, descriptive median/MAD/range, bucket coverage, and quality flags. Individual observation records, including qualitative home-test results, can also be displayed one by one; categories such as positive remain categorical and are not averaged or interpreted as ovulation, fertility, pregnancy, or diagnosis. Numeric summary and individual-record paths stay separate. The measurement view does not infer trends, baselines, hormone levels from wearable proxies, cause, or clinical meaning. These views display selected files in the current tab only; they do not write to browser storage, Matrix, or the AI provider and clear on refresh/close. The file itself is not an authorization credential: the client cannot verify consent grants, identity, or authority, so the summary or record file must already have been prepared from explicitly authorized records by a trusted caller. The client does not collect or persist a cycle history or measurement series.

The chat's optional **Metheus AI** panel sends `!metheus ai-info`, `!metheus ai-status`, `!metheus ai-opt-in`, and `!metheus ai-opt-out` commands as visible room messages. Participants must read the returned disclosure and opt in individually; the bot refuses AI processing until every currently joined person is opted in. `!metheus ai-status` reports aggregate consent counts, not individual choices or chart settings. The panel offers one-turn `ask-chart` and temporary `chart-set` / `chart-status` / `chart-clear` controls. These use the sender's self-attested gate list; the bot does not calculate or authenticate chart ownership. The bot adds complete channels and optional complementary activity ideas from version-matched local catalogs. Commands and replies are visible to the room and may remain in Matrix history. A `chart-set` profile stays in bot memory only, until cleared, any member opts out, membership changes, or the bot restarts; `chart-status` reports only the requesting sender's own setting. Chart-aware turns are isolated from shared AI conversation history and do not add their question or answer to it, keeping one participant's gate context out of later participants' prompts. Ordinary room messages are not forwarded to the AI. Each model-bound message uses a temporary room-local participant ordinal instead of a Matrix ID. If membership, consent, or the chart setting changes while a request is in flight, the bot discards its pending room reply, though a provider request already sent cannot be recalled.

The separate **Set Metheus’s symbolic gates** panel configures an optional prompt-style profile, not a chart belonging to the AI. Its selected gates are stored in this browser's `localStorage`; they are included in a Matrix command and sent to the AI provider only when the sender chooses **Ask once with both maps**. The command has two clearly named lists: `my-gates` and `metheus-gates`. The bot derives each set's complete channels independently and tells the model that Metheus has no body or lived Human Design experience. The AI profile does not affect ordinary chat or future `chart-set` turns. **Compare on BodyGraph** overlays the sender's currently selected gates in amber, the local Metheus prompt profile in teal, and shared gates/channels in violet. Text describes each map's channel set and their overlap. This is a symbolic structure comparison; it cannot establish compatibility, traits, biology, or an interpersonal relationship.

The **Generate input prompt from selected maps** control uses the shared `generateBodygraphInputPrompt` function. It turns the currently selected gate lists into a readable prompt containing each map's gate set, topology-defined complete channels, centers connected by those channels, and explicit interpretation limits. Smaller selections include the catalog's optional activity descriptions; larger prompts switch to a compact form that keeps all gates, channels, and centers while omitting per-gate descriptions to stay within the bot's input limit. The generated text can be copied for another AI or inserted into a room-visible one-turn Metheus draft, where the bot also receives the versioned structured map context. Changing either selection clears the generated prompt so stale map data is not reused.

## Three.js bodygraph reference

The chat places a Three.js/WebGL-rendered bodygraph beside the room timeline on desktop; on narrow screens the panel starts closed and its Three.js module loads only when the panel is opened. It uses vector geometry from the shared Astrolabe Human Design bodygraph template, with its embedded scripts removed and all natal/transit activation values, personal status, and source-specific labels stripped. The reference has no participant chart data. Drag to orbit, scroll/pinch to zoom, click a gate/channel to highlight it, or enter a reference such as `Gate 34` or `Channel 34-20`. A collapsed **Browse gates and channels as a text list** section offers keyboard-accessible buttons for all geometry-extracted gates and channels; choosing one highlights the same generic map and describes a gate's center or a channel's two endpoint gates and centers in the detail panel. Gate/channel mentions in room messages are also highlighted when the diagram is open. Selecting self-reported gates in the AI idea catalog highlights those gates together on the generic BodyGraph and highlights any channel whose two gates are both selected; a plain-language summary names completed channels. This is a temporary symbolic calculation from the selected list, not a verified personal chart. The **How the layers fit together** guide gives a plain-language distinction between Promethean symbolic prompts and Epimethean lived records, with an example showing why a chart prompt cannot explain sleep or reveal a hormone level. The local cycle-day viewer displays a precomputed JSON view in the browser tab, with labels and values from the selected records; the local measurement viewer displays either a numeric-series summary or selected observation records, including qualitative home-test categories, one by one. Neither viewer writes to browser storage or sends its imported file or displayed values to Matrix or the AI provider; a user would have to separately compose a room message, and any room message is visible according to Matrix room settings. These viewers do not verify the authorization or identity claims associated with a file. The **Gate links** view overlays source-attributed gate correspondences from a separate catalog; users can select a marked gate or an equivalent keyboard-accessible list entry to display the source and limits. Rings mark symbolic source claims, not tested gate-to-body mechanisms or personal measurements. The **Body systems** view displays a separate interactive candidate physiology graph, with domain filtering and node details; physiology-node positions are diagram layout, not anatomy, and the graph remains under review and internal only. Neither map calculates a chart or makes personal health inferences. Update the static JSON files in `pwa/public/` when their source catalogs change; contract validation checks that the PWA copy stays synchronized.

## Room setup required

1. Use the Castalia Matrix homeserver at `https://matrix.castalia.institute`; its `oidc-supabase` SSO provider authenticates through Castalia.Institute. The homeserver must allow browser access (CORS) for the deployed Metheus origin.
2. Create a private room for the intended participants. Decide who may invite members, whether room history is shared with new members, how long messages are retained, and how the room will be closed or deleted.
3. Enable Matrix end-to-end encryption for the room and verify that the bot account is designed to participate in encrypted rooms. Encryption at the Matrix transport layer alone is not end-to-end encryption.
4. Invite each adult participant and the Metheus bot. Give each person their own account; do not share passwords or access tokens.
5. Make the bot's role, AI provider, model processing, retention, and escalation limitations clear to all participants before they disclose personal information. The bot should not represent itself as a therapist, clinician, mediator, or relationship judge.
6. Open `/chat/` and choose **Sign in with Castalia.Institute**. After SSO, the PWA exchanges the one-time Matrix login token and lists rooms already joined by that account. Select a room to open it, or enter a room ID/alias to join an invited room. Room creation and invites happen in a Matrix client or admin interface, not in this static PWA.

The current client does not provide room creation/invites, participant-specific charts, cycle-data collection or persistence, device verification/recovery UX, user management, an independent consent-state dashboard, moderation, transcript export/deletion, or message pagination and file/media support. Its command buttons send visible Matrix messages; they do not verify participant devices or certify consent. The encryption check reports the room setting but does not verify participant devices, verify bot key handling, or certify the service. Treat it as an early client, not a secure health-data product. Before using it for reproductive, health, or intimate information, complete a security/privacy review, add trusted device verification and recovery flows, and establish an appropriate retention plan. Do not use it for children's personal data in this prototype.

## Build and deploy

The Pages workflow runs `npm ci --prefix pwa` and `npm run build --prefix pwa`, then publishes the repository root. The Vite build writes the static PWA to the ignored `chat/` directory. Local build: `npm ci --prefix pwa && npm run build --prefix pwa`.

The client is configured for the custom domain path `/chat/`. Its installable shell works offline after first load, but Matrix sign-in, room sync, encryption key fetches, and message exchange require network access. Do not treat the offline shell as offline chat.
